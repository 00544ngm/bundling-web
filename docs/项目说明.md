# A+B 组合选品平台 · 项目说明

> 本文讲**这个项目是什么、怎么运转、为什么这么设计**。
> 部署步骤见 [DEPLOY.md](../DEPLOY.md)，逐次改动的原因与验证见 [优化迭代记录.md](优化迭代记录.md)。

---

## 1. 解决的问题

Walmart 跨境卖家选品时，真正难的不是"这个商品好不好卖"，而是
**"主品该和什么辅品一起卖"** —— 组合能不能成立、客单价能不能提上去、
辅品的差评能不能被主品补上。

人工做这件事要：扒商品页 → 翻几十条评论 → 逐个猜搭配 → 挨个查 1688 有没有货。
一个主品能耗掉半天，而且结论不可复现。

本项目把这条链路自动化：**输入主品链接，输出一组带证据、带评分、可复核的辅品方向与组合方案。**

## 2. 三个指令

整个业务逻辑围绕三段"指令"展开（提示词都在 `app/infrastructure/llm/prompts/`）。
它们**不是三个独立功能，而是一条递进的流水线**。

### 指令A · 假设生成（`hypothesis_service.py`）

输入主品的商品页与评论，产出若干**结构化的辅品方向**。

每个方向带：名称、类型、动机、证据等级、粘性分、关键词包。
LLM 负责"想出方向"，**分数由服务端算**（见 §4）。

### 指令B · 审判（`judgment_service.py`）

给一批**指定的辅品候选（B 品）**，逐个审：

| 环节 | 回答什么 |
|---|---|
| 假设对齐审查 | 候选与原始假设是否一致？冲突时以真实数据为准 |
| 动机复核 | 消费者为什么会一起买？ |
| 价格数学实算 | 加价后落在什么价位带？ |
| 用户理性审查 | 用户会理性地这样搭配吗？ |
| 一票否决 | 有没有硬伤足以直接否掉？ |
| 双评分 | C 组合价值分 + B 跨境执行分 |
| 判级与排序 | 给结论与推荐等级 |

提示词是 `judgment_b.txt`，判定口径为 **V2.1**（带 `gate_status` / `needs_verification`）。

### 指令C · 完整组合方案（`bundle_plan_service.py`）

**只在已有评分结果之上工作**。把主品与辅品组成"主品 + 1/2/3 件"的完整组合，
对每个组合做：

- **加件/减件检验** —— 每件辅品去掉会损失什么、加上能得到什么
- **8 种反事实比较** —— 只在主品、用户已有全套、别的搭配方式等
- **双通道输出** —— 前三名 + 探索性候选

**设计上"永不抛异常"**：整个 `build` 全捕获，失败时返回 `unavailable_block`
而不拖垮整个任务 —— 指令C 是**加分项**，不该让主流程失败。

## 3. 技术架构

```
┌─────────────┐
│  Next.js 15 │  App Router，客户端组件为主
└──────┬──────┘
       │ HTTP + Bearer 令牌
┌──────▼──────────────┐
│  FastAPI（backend/）│  鉴权 / 分组门禁 / 任务提交 / 结果查询
└──────┬──────────────┘
       │ 入队
┌──────▼──────┐
│ Redis / ARQ │  任务队列
└──────┬──────┘
       │
┌──────▼────────────────────────────┐
│  Worker（backend/workers/jobs.py）│  ← 真正干活的地方，max_jobs=1
│   ① 按 api_group_id 解析出 provider │
│   ② 抓取（CDP Chrome）              │
│   ③ 指令A / 指令B / 指令C           │
│   ④ 服务端评分 + 结果质量校验        │
└──────┬────────────────────────────┘
       │
┌──────▼──────┐
│ PostgreSQL  │  任务 / 结果 / 用户 / 分组 / 供应商配置
└─────────────┘
```

### 分层职责

| 目录 | 职责 | 约束 |
|---|---|---|
| `app/domain/` | **纯逻辑**：评分、配对策略、产品类型判定 | 不依赖 Web 框架，是纯函数，可直接单测 |
| `app/infrastructure/` | 外部世界：浏览器、LLM、爬虫、存储 | 只被上层调用 |
| `app/services/` | 指令A/B/C 的服务层 | 编排 domain + infrastructure |
| `backend/` | Web 层：路由、鉴权、任务编排、Worker | 依赖 `app/`，反向不成立 |
| `frontend/` | 界面 | 只通过 `/api/v1` 通信 |

### 一次任务的完整链路

```
1. 前端 POST /jobs/hypothesis
2. 后端按登录者的 api_group_id 记录作用域，写库，入队
3. Worker 取任务：
   a. 用任务的作用域解析出 provider 客户端（此处已固化，见 §4）
   b. Playwright 连 CDP Chrome → 抓商品页 + 评论（含人机验证等待）
   c. 指令A → 结构化方向
   d. 服务端评分（粘性分等）
   e. 若开启指令C → 组合方案
   f. result_quality 校验结果
4. 结果写回 PostgreSQL，前端轮询展示
```

## 4. 四条核心设计原则

这四条是这个项目最不能破坏的东西。改动前请务必确认没有违反。

### ① 所有数值评分在服务端，LLM 只做定性

`app/domain/stickiness.py` 等是**纯函数**。LLM 负责推理与描述，
**不得输出分数**。

`backend/application/result_quality.py` 会强制校验模型输出里
**不允许出现 `final_score` / `score_cap`** —— 一旦出现就判结果不合格。
这是为了防止模型"自己给自己打分"污染可复现性。

### ② 模型作用域在 Worker 的工厂函数处固化

链路：

```
user.api_group_id
  → 提交时写进 request_payload
  → Worker: _create_provider_resolver(session, group_id)
  → ProviderClientResolver(group_scoped=True)
  → 拿到成品 llm 客户端
  → 传给 AnalysisRunner（内部完全不做 provider 解析）
```

**后果**：员工无法越组选模型，**即使篡改请求体也没用** —— 服务端按登录者身份解析。
`AnalysisRunner` 对作用域零感知，所以新增分析阶段不会破坏这条边界。

### ③ 结果不可重算

旧任务的结果是**历史快照**。未经明确授权，不得重新计算或覆盖。
展示层只读。

### ④ 一切改动都要留痕

`docs/优化迭代记录.md` 是本项目的**权威变更记录**，约 5000 行。
每次改动必须追加：目标、范围、验证结果、失败案例、已知限制、回滚提交。
**不得删除历史失败记录。**

## 5. 鉴权与权限模型

- **登录**：PBKDF2-HMAC-SHA256（21 万次迭代）+ PyJWT HS256，令牌 TTL 30 天
- **首次登录强制改密**：播种的 admin 与管理员重置过的密码，都必须改
- **两种角色**：`admin` / `employee`

### 接口分组（三层结构）

```
ApiGroup（组：自己的 base_url / key / 模型集）
   └── ApiGroupProvider（组内某家供应商）
          └── ApiGroupProviderModelValidation（组内逐模型的验证/勾选状态）
```

员工通过 `User.api_group_id` 绑组。**员工只能用本组已验证且已勾选的模型。**
`/workbench/providers` 是任务模型选择器的**唯一来源**（按登录者作用域裁剪）。

> 管理端的 `/settings/providers`（全局配置）是另一套，路由级要求 `require_admin`，
> 且默认只允许从本机访问。

## 7. 模型能力约定（关键参数）

不同模型对参数的支持差别很大，代码里用**按模型名前缀匹配**的表来适配
（都在 `app/infrastructure/llm/__init__.py`）。改错会直接导致 400 或静默降质。

| 参数 | 表 | 作用 |
|---|---|---|
| `max_completion_tokens` vs `max_tokens` | `_MODELS_USE_COMPLETION_TOKENS` | gpt-5 系 / o 系要用前者 |
| temperature 是否可传 | `_MODELS_NO_TEMPERATURE(_PREFIX)` | gpt-5.5/5.6 系、Kimi 系**不接受**该参数 |
| 结构化报告超时 | `_SLOW_STRUCTURED_REPORT_MODELS` | 默认 120 秒；慢模型给 600 秒 |
| 输出 token 预算 | `_REASONING_STRUCTURED_OUTPUT_MODELS` | **推理模型**给 65536，普通档 16384 |
| 推理强度控制 | `_THINKING_UNSUPPORTED_EFFORT_MODELS` / `_THINKING_DISABLED_MODELS` | 见下 |

### 推理强度（踩过坑，务必理解）

旗舰推理模型默认会把输出预算大量烧在**隐藏思维链**上，表现为
**跑很久之后返回空内容**。而且各家的开关**互斥**，同时传会被上游拒绝：

| 模型族 | 能不能关掉思考 | 我们传什么 |
|---|---|---|
| `kimi-k3`、`glm-5.3`（含 flash） | ❌ 关不掉 | `reasoning_effort: "low"`（默认是 max） |
| `kimi-k2.6`/`k2.5`、`glm-5.2`/`glm-5`/`glm-4.6`/`glm-4.5` | ✅ 可以关 | `thinking: {"type": "disabled"}` |
| `glm-4.7`、`kimi-k2.7-code` | ❌ 关不掉 | **什么都不传**（传了会被拒） |

新增供应商时，**务必先查官方文档确认这几个参数的支持情况**，然后加进对应的表。

## 8. 任务状态与生命周期

```
queued → running → completed
                 ↘ failed
                 ↘ interrupted   （进程被中断，需手动重提）
```

- Worker 是 `max_jobs=1` —— **同时只跑一个任务**，其余排队
- Worker 启动时会把上次进程残留的 `running` 任务标记为 `interrupted`
  （单 worker 部署下安全；多副本部署必须关掉这个开关）
- 失败任务可以「重新提交」→ **新建一个任务**（另一个 id），不是原地重试

## 9. 怎么加一家新供应商

以加一家 OpenAI 兼容的厂商为例：

1. **`backend/application/provider_service.py`** 的 `PROVIDER_SLOTS` 加一个槽位
   （类型 / 协议 / 显示名 / base_url / 默认模型）
2. **`backend/api/schemas/providers.py`** 的 `ProviderSlug` 加上新 slug
3. 若它能当主模型：**`backend/api/schemas/jobs.py`** 的 `TaskProvider` 也加上
4. **`frontend/lib/api/types.ts`** 的 `ProviderSlug` 同步
5. **`frontend/lib/model-label.ts`** 加显示名
6. 若它是推理模型：按 §7 决定要不要加进那几张参数表
7. 跑 `backend/tests/test_provider_service.py` 里断言槽位集合的测试并同步更新

**不需要数据库迁移** —— `provider_configurations.slug` 是普通字符串列，
新厂商只是新增几行数据。

## 10. 已知限制

| 限制 | 说明 |
|---|---|
| **人机验证** | 抓取遇到 Walmart CAPTCHA 是人工流程，需要有人在浏览器里点。headless 环境下会等满超时失败 |
| **单 worker** | `max_jobs=1`，同一时间只处理一个任务，慢任务会阻塞后面的 |
| **HTTP 部署** | 令牌明文传输，建议上 HTTPS（需要域名） |
| **推理模型较慢** | `glm-5.3` 单次完整报告约 270~440 秒；Kimi 更慢，可能触及任务级超时上限 |
